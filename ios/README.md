# CKey Reader for iPhone

This is an early native camera test app for CKey Profiles 0–3. It locks capture to the physical rear wide camera and hands each frame's luma plane to the shared core's one-call scan, `ckey_scan_frame_gray8`: the core finds bright and dark connected border candidates, refines each one against the printed Grid, Ring, Ray, and finder keys, and tries the decoders for Profile 0 and then Profiles 1, 2 and 3. The app itself locates and decodes nothing. There are no fixed symbol-size ladders, and successful reads still require native framing, Reed–Solomon, and CRC validation. `src/ckey.cpp` is compiled directly into the app so there is no second encoder/decoder implementation. Profile 1 has optical fixtures; Profiles 2 and 3 are experimental camera paths and require physical testing before any reliability claim.

This app is a bare test harness: whole frames only, no region of interest, no tracking and no camera control. The camera layer that owns the camera (region decoding, tracking, exposure, focus and zoom from the core's advice, and the optional brackets) is the Swift SDK's `CKeyCameraScanner`; see [sdk/swift/README.md](../sdk/swift/README.md).

## Run on a phone

1. On a Mac with Xcode, open `ios/CKeyReader.xcodeproj`.
2. Connect and unlock the iPhone, then select it as the run destination.
3. In **Signing & Capabilities**, choose your Apple development team. The bundle identifier is `solutions.clearkey.CKeyReader`; change it if your team requires a unique identifier.
4. Press **Run** and allow camera access when iOS asks.
5. Display a CKey symbol on a separate screen or print it. Keep the whole symbol in view and move closer until the key and module details are clear.

## Verify the build has the current core

The version line under the title must read **`0.1.0-build.120`**, which is `ckey_get_software_version()` from the compiled core. If it shows an older version, Xcode built a stale copy: run **Product → Clean Build Folder** (⇧⌘K) and rebuild.

Then confirm, with symbols generated by a CKey Renderer built from the same commit:

- **P0 decodes at every size.** Generate Profile 0 symbols in the renderer (the default profile). The reader shows `Profile 0 · v<N>`; the version comes from the symbol's keys.
- **P1, P2, and P3 each decode.** Older P2/P3 renders (formats 0.23/0.24, from before dev.49) do not decode from images; regenerate them.
- **P3 decodes only when the symbol is large in the frame.** The reader prefers 4K capture, and P3 needs at least 11 camera pixels per symbol unit, so its border must span at least about 60% of the frame's short side. Its whole border must stay in view; at 1080p capture it cannot decode P3 at all. The live diagnostics show the measured border side.
- **Rotation doesn't matter.** Border finding and refinement run in the shared core (inside `ckey_scan_frame_gray8`), and the simulated-reader test decodes symbols rotated up to 33° with keystone and blur.

The result is shown as hexadecimal text, with the profile label and payload length. **Detection** and **CKey** timings are now the same number: the time of the one core scan call for that frame (localization and decoding together). They are per-frame timings, not benchmark statistics. While nothing decodes, the live line shows the leading candidate's measured side, its Profile 0 fit score and whether its border is cut by the frame edge.

## Current limits

- Every profile's decoder is tried on each candidate (by the core's scan call); the shared core's profile framing, Reed–Solomon code, and CRC gate successful reads.
- It scans grayscale Y planes from the camera (4K when the device supports it, otherwise 1080p) and supports either symbol polarity through the shared core. The border search samples about 960 × 540 points at any capture size.
- The app has not been compiled or run on an Apple device in the current build environment. The C++ core's image fixture tests do not verify AVFoundation camera behavior.
- Lighting, distance, blur, rotation, perspective, glare, minimum module size, and device latency have not been characterized. No sub-200 ms or camera-reliability claim is made.
- Full-frame localization is based on mathematical border/key fitting but still needs a labelled real-camera corpus, including lens-distortion, distance, blur, damage, and noise captures. Profiles 2 and 3 need physical-device tests before any end-to-end speed or reliability claim.
